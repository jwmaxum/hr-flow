# ERP 0단계 회사별 업로드 양식 명세

2026년 11월 11일 작성. 제공된 품목명·단가·수량·금액은 **재고관리 구조를 확인하기 위한 Mockup 데이터**다. 각 회사는 자신의 품목과 가격을 입력하며, 업로드한 자료는 로그인한 회사의 DB에만 저장하도록 설계한다.

이번 산출물은 입력 양식 2종과 업로드·검증 규약이다. 파일 생성으로 DB가 변경되지는 않는다. 회사별 업로드 API와 DB 반영 기능은 개발계획서의 1~2단계에서 구현한다.

## 1. 산출물과 사용 방법

| 파일 | 내용 |
| --- | --- |
| [기초재고 입력 양식](기초재고_이관_입력양식.xlsx) | `작성안내`, 빈 `이관입력`, 106개 Mockup 품목의 `참고데이터`로 구성한다. 회사별 품목·창고·기초수량과 단가 또는 장부금액을 입력한다. |
| [거래별 입출고 양식](거래별_입출고_입력양식.xlsx) | `작성안내`, 빈 `거래입력`, 합성 거래 5행의 `작성예시`로 구성한다. 회사별 거래일·입출고·품목·수량·단가·거래처를 입력한다. |

두 파일의 실제 입력 시트는 비워 두었다. 노란색은 입력 영역, 회색은 참고 계산 영역이다. 각 회사의 품목명·단가·창고·거래처를 직접 입력할 수 있으며 106개 품목에 맞출 필요가 없다. `참고데이터`와 `작성예시`는 업로드 대상에서 제외한다.

실제 입력은 각 파일의 `작성안내` B5에 회사명을, B6에 기초재고 기준일을 적은 다음 진행한다. 회사명은 사용자의 확인용이며 시스템 권한은 로그인 세션으로 판단한다. 기준일은 해당 날짜 마감 재고를 뜻하며, 거래별 입출고는 다음 날부터 반영한다.

## 2. 기초재고 입력 규격

`이관입력`의 9행은 머리글이고 10~209행에 최대 200개 입력 행을 제공한다. DB 입력 영역은 A:P, 참고 계산 영역은 Q:S다. 행 수를 확대할 때 같은 열 정의와 수식을 유지한다.

| 열 | 필드 | 규칙 |
| --- | --- | --- |
| A | 행번호 | 양의 정수. 파일 안에서 중복 불가. 오류 안내와 재검증에 사용한다. |
| B~E | 품목코드·품목명·규격·단위 | 회사가 자유롭게 지정한다. 품목코드는 텍스트로 보존하며 선행 0을 유지한다. 코드·품목명·단위는 필수다. |
| F~H | 과세구분·계정과목·그룹명 | 회사의 품목 분류. 과세/영세/면세를 구분하고 나머지는 회사 필요에 따라 입력한다. |
| I~J | 창고코드·창고명 | 회사에 등록된 창고를 사용한다. 공란은 미리보기에서 실제 회사 창고로 매핑한 뒤 확정한다. |
| K | 기초수량 | 0 이상 숫자. 공란과 숫자 0을 구분한다. |
| L | 금액입력방식 | `단가` 또는 `금액` 중 하나를 선택한다. |
| M | 기초단가 | 단가 방식을 선택했을 때 입력한다. 판매가격이 아닌 기초재고의 단위 원가다. |
| N | 기초금액 | 금액 방식을 선택했을 때 회사 장부의 재고금액을 입력한다. |
| O~P | 통화·비고 | 1차 재고 장부는 KRW. 무상 재고나 산정 근거를 기록한다. |
| Q~S | 반영금액·평균원가·입력점검 | 참고 수식이며 DB 입력값에 포함하지 않는다. 서버가 다시 계산한다. |

단가 방식을 선택하면 기초금액 입력란은 비우고, 반영금액은 `ROUND(기초수량 × 기초단가, 0)`으로 계산한다. 금액 방식을 선택하면 기초단가 입력란은 비우고 회사 장부금액을 보존한다. 선택하지 않은 입력란까지 채우면 두 값의 충돌로 표시한다.

평균원가는 반영금액을 기초수량으로 나눈 참고값이며 수량 0이면 공란으로 표시한다. 재고금액을 평균단가로 역산했다가 다시 곱하여 장부금액을 바꾸지 않는다. 수량 0·금액 0은 허용하고, 수량 0·금액 비영은 오류로 표시한다. 수량 양수·금액 0은 실제 무상 취득 근거를 확인한다.

## 3. 거래별 입출고 입력 규격

`거래입력`의 9행은 머리글이고 10~209행에 최대 200개 입력 행을 제공한다. DB 입력 영역은 A:AA, 참고 계산 영역은 AB:AF다.

| 열 | 필드 | 규칙 |
| --- | --- | --- |
| A~E | 거래일·처리순서·구분·거래번호·행번호 | 기준일 이후 실제 날짜, 날짜 내 처리순서, 입고/출고, 문서번호와 품목 행번호를 입력한다. |
| F~K | 품목코드·품목명·규격·단위·창고코드·창고명 | 회사의 기준정보와 대조한다. 회사별로 다른 품목명과 단가를 사용할 수 있다. |
| L~O | 수량·단가·통화·적용환율 | 수량은 양수. 입고는 매입단가, 출고는 판매단가. 환율은 1 외화당 KRW이며 KRW는 1이다. |
| P~R | 부가세구분·부가세율·단가기준 | 과세/영세/면세, 실제 세율, 세금포함/세금별도를 선택한다. 영세·면세는 세율 0을 사용하되 구분을 보존한다. |
| S~V | 거래처코드·거래처명·국가코드·등록번호 | 기존 거래처코드 우선. 신규는 이름·국가를 입력하고 등록번호로 후보를 대조한다. 번호가 없으면 수동 확인한다. |
| W~AA | 담당자·이메일·연락처·주소·비고 | 다음 거래에서 재사용할 정보와 거래 증빙·환율·무상 근거를 입력한다. |
| AB~AF | 공급가액·세액·총액·원화공급가액·입력점검 | 참고 계산 영역이며 서버가 입력값으로 다시 계산한다. |

한 행은 한 문서의 한 품목이다. 같은 문서의 여러 품목은 거래번호와 처리순서를 같게 하고 행번호를 달리한다. 회사 안에서 거래번호+행번호 조합은 유일해야 한다. 같은 문서는 거래일·입출고구분·거래처·통화가 같아야 한다. 같은 날짜의 서로 다른 문서에는 서로 다른 처리순서를 부여한다.

1차 양식은 KRW·USD·EUR·JPY·CNY를 지원하는 검토안이다. KRW·JPY는 0자리, USD·EUR·CNY는 2자리로 행별 금액을 반올림한다. 세금별도는 수량×단가를 반올림해 공급가액을 구하고 공급가액×세율을 반올림해 세액을 구한다. 세금포함은 수량×단가를 반올림해 총액을 구하고, 반올림 전 수량×단가를 `(1+세율)`로 나누어 반올림한 공급가액과의 차이를 세액으로 둔다. 원화공급가액은 공급가액×환율을 원 단위 반올림한다. 회사별 실제 세금·회계 기준은 구현 전 검토한다.

출고원가는 판매단가와 구분하여 서버가 승인한 평가 방식으로 계산한다. 잔량과 잔액은 회사별 기초재고 및 확정 원장에서 계산한다. 이 양식은 원장이나 현재고를 대체하지 않는다. 반품·취소·소급정정·창고이동은 원거래 연결이 필요하므로 음수 수량으로 우회하지 않고 2단계에서 전용 흐름을 구현한다.

## 4. 회사별 DB 반영 설계

1. **파일 수신과 검증**. 로그인 사용자의 활성 회사와 ERP 권한을 확인하고 지정된 입력 시트·범위만 읽는다. 파일의 회사명·품목코드·경로가 다른 회사에 대한 권한을 부여하지 않는다.
2. **기준정보 대조**. 회사 안에서 품목코드와 창고를 찾는다. 신규 품목은 회사별 신규 등록 후보로 표시한다. 기존 코드의 품목명·규격·단위가 다르면 확인을 요구한다. 다른 회사의 품목을 검색하거나 수정하지 않는다.
3. **거래처 처리**. 기존 거래처코드 또는 회사 내 국가+등록번호로 대조한다. 등록번호가 없거나 유사 이름만 일치하면 사용자가 선택한다. 확정 저장 시 신규 거래처를 자동 저장하여 다음 입력에서 재사용한다.
4. **미리보기**. 품목 신규/기존 여부, 회사별 창고, 수량·단가·금액, 오류 원본행과 확정 시 잔량·잔액 변화를 보여준다. 파일을 올린 시점에는 재고를 변경하지 않는다.
5. **확정**. 사용자가 확인하면 서버가 권한·현재고·중복·마감·금액을 다시 검증하고 회사별 기초재고 또는 입출고 원장과 현재고를 함께 반영한다. 같은 파일을 다시 확정해도 중복 반영하지 않는다.

예정 데이터 구조는 회사 경로 아래 `items`, `warehouses`, `partners`, `imports`, `stockMovements`, `inventoryBalances`를 분리하는 방식이다. 실제 컬렉션명은 구현 시 확정한다. 품목 식별은 회사와 품목코드의 조합이다. 예를 들어 회사 A와 회사 B가 모두 `0001`을 사용해도 품목명·매입단가·판매단가·재고는 독립적이다.

업로드의 단가는 해당 회사의 해당 거래 가격으로 보존한다. 기존 품목의 기본단가나 과거 거래 가격을 자동 덮어쓰지 않는다. 기본단가 갱신이 필요하면 별도 선택과 변경 이력을 둔다.

기초재고 중복은 회사·기준일·품목·창고 및 처리 식별값으로 검증한다. 거래 중복은 회사·거래번호·행번호와 파일 식별값으로 검증한다. 공통 Mockup 품목을 모든 회사에 초기 데이터로 배포하지 않는다.

## 5. 창고 공란과 음수 3건의 처리

현재 자료는 Mockup이므로 실사나 실제 장부 수정을 요청하는 대상이 아니다. 다음의 **업로드 검증 사례**로 사용한다.

| Mockup 조건 | 미리보기 동작 | 확정 조건 |
| --- | --- | --- |
| 106행의 창고 공란 | `창고 미지정` 표시. 회사의 기존 기본창고 일괄 선택 또는 품목별 창고 매핑 제공. | 사용자가 실제 회사 창고를 선택해야 한다. 시스템이 임의로 창고를 만들거나 다른 회사 창고를 사용하지 않는다. |
| 기말수량·금액 공란 49행 | 필수 수치 누락 표시. 공란을 자동 0으로 만들지 않는다. | 숫자 0을 포함한 실제 값을 입력하거나 사용자가 명시적으로 제외한다. 제외된 행은 결과에 기록하고 조용히 누락시키지 않는다. |
| 코드 123, 수량 -270, 금액 -1,377,460 | 음수 수량·금액 오류 표시. | 수정 후 재검증. 자동 0 처리 또는 자동 제외하지 않는다. |
| 코드 167, 수량 -74, 금액 -37,000 | 같은 음수 검증 적용. | 수정 후 재검증. |
| 코드 25, 수량 -40, 금액 공란 | 음수 수량과 금액 누락을 함께 표시. | 두 문제를 모두 해결한 뒤 재검증. 판매금액으로 원가를 채우지 않는다. |

음수 3건의 수량 합계는 -384개다. 기록된 음수 금액 합계는 -1,414,460이며 코드 25의 금액은 공란이다. 자동 제외하면 총괄 합계가 달라지므로 오류 행과 제외·수정 내역을 투명하게 표시해야 한다. 이는 예외처리 검증을 위한 숫자이며 회사별 운영재고의 기준값이 아니다.

실제 업로드에서 같은 문제가 발생하면 해당 파일은 검토 상태로 유지한다. 기본 정책은 오류를 수정한 후 파일 전체를 확정하는 것이다. 부분 확정은 사용자가 대상 행을 명시 선택하고 제외 내역·재처리 상태를 추적할 수 있는 별도 기능으로 구현한다.

## 6. 검증과 후속 개발

참고 Mockup의 106개 품목에 대해 수량·재고금액·마진 대사와 10개 합계 열 일치를 확인했다. 원본 수치 영역의 공란 298셀은 대사 계산에서만 0으로 취급하고 참고 시트에는 공란을 보존했다. 원본 XLS는 구조 오류가 있어 조사용 복구 판독을 사용했다. 이 파일을 실제 운영 업로드 표준으로 채택하지 않고 새 `.xlsx` 입력 양식을 사용한다.

Excel에는 매크로·외부 연결·인감 이미지가 필요하지 않다. 입력 영역의 수식은 거절하고 영역 밖의 참고 수식은 실행하거나 신뢰하지 않는다. ERP 서버는 허용 시트·범위·파일 크기·압축 해제량·행 수를 제한하고 모든 금액을 독립 계산한다. 기존 급여 파일 검증과 별개인 ERP 파서 규약으로 구현한다.

다음 개발은 1단계의 ERP 진입 버튼과 회사별 품목·창고·거래처 관리다. 이어서 2단계에서 이 두 양식의 업로드 미리보기와 회사별 DB 확정을 구현한다. 개발 검증에는 같은 코드지만 품목명·단가가 다른 회사 2개를 사용하여 회사 간 조회·변경·업로드가 차단되는지 확인한다.

문서 3종의 최종 출력 시안과 상세 권한표는 0단계 후속 설계 항목이다. 이번 작업은 사용자가 요청한 두 Excel 양식과 창고·음수 처리 규약까지 완료한 범위다.
