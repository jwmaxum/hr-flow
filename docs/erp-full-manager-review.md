# ERP관리자 전체 권한과 주요 변경 점검

기준일: 2026-11-15

## 권한

ADMIN은 기존과 같이 ERP 전체 업무를 처리합니다. SUB_ADMIN 직원에게 별도의 ERP 담당 업무 **ERP관리자(MANAGER)** 옵션을 지정하면 ADMIN 승인 없이 입고·출고, 수량·금액 조정, 취소·반품, 수금·배분·반환, 거래명세표 발행·정정, 승인 요청 처리, 월마감 확정·재개방, 마감 계획·체크리스트와 ERP 담당자 권한 관리를 할 수 있습니다.

ERP관리자 옵션은 일반 직원에게 지정할 수 없으며, 자신의 권한 변경도 허용하지 않습니다. 이 옵션은 HR의 ADMIN 권한으로 승격시키지 않습니다. 회사별 데이터 분리와 비활성 계정 차단, 월마감 잠금은 유지합니다. 마감된 기간의 거래는 재개방 절차 이후 수정합니다. 마감 계획의 담당 항목 제출은 배정 담당자가 수행하고 관리자는 검토·체크리스트·마감을 처리합니다.

다른 입고·출고 담당자의 수정·삭제 요청은 기존 승인 절차를 유지하며, ADMIN 또는 ERP관리자가 승인할 수 있습니다. 확정 거래와 발행 서류는 이력을 지우는 삭제 대신 취소·정정 기록을 남깁니다.

## ADMIN 확인 방법

1. ERP → 대시보드 → **월별 대시보드 → 주요 변경 점검**을 엽니다.
2. 조회 기간과 변경 유형을 선택합니다. 기본 기간은 대시보드의 선택 월이며, 처리 시각의 한국 날짜를 기준으로 조회합니다. 거래 기준일과 처리일은 다를 수 있습니다.
3. 재고 변동, 거래 수정·정산, 취소·삭제·사용중지, 거래서류 변경, 월마감·승인, 기준정보·권한별 건수를 확인합니다.
4. 표에서 담당자, 처리 시각, 사유, 문서번호, 직접 처리·승인 구분을 확인하고 상세를 펼쳐 변경 전후 값을 비교합니다. 거래서류에는 수량·단가·공급가액·부가세·합계도 표시됩니다.
5. **ADMIN 확인 상태 → 미확인 중요 변경**으로 조회합니다. 내용을 검토한 행의 **이 변경 확인 완료**를 누르거나, 현재 페이지에서 여러 행을 선택한 뒤 **선택 N건 확인 완료**를 누릅니다.
6. **확인 완료** 필터에서 최초 확인 ADMIN과 시각을 확인합니다. 확인 표시는 회사에 공유되며 ERP관리자는 조회만 합니다.
7. 전체 이력 버튼으로 원본 변경 기록을 확인합니다.

한 작업의 분할 이력은 한 건으로 계산합니다. 한 작업이 여러 유형에 포함될 수 있어 유형별 건수의 합이 전체 건수보다 클 수 있습니다. 한 번에 93일 이내를 조회하며, 1,000개 이력 또는 20MiB를 넘으면 기간을 좁히도록 안내합니다. 일부만 합산하지 않습니다. 화면은 30건씩 조회하며 상세는 앞 40개 변경 기록, 문서는 앞 20개 변경 행을 표시합니다. 전체 원본은 변경 이력에 보관됩니다.

## 중요 변경 알림과 확인 기록

- 상단 **변경 확인** 버튼과 ADMIN의 **오늘 할 일 → 누적 미확인 중요 변경**에서 누적 점검함으로 이동합니다. 이전 달·이전 연도를 포함한 미확인을 오래된 순으로 30건씩 표시합니다. 기간별 변경 이력에서는 확인 완료 내역과 최초 확인자·시각을 조회합니다.
- 재고, 거래·정산, 취소·삭제·사용중지, 거래서류 변경과 기존 품목의 매입·판매단가 변경이 확인 대상입니다. 신규 입출고·수금·문서 생성도 포함합니다. 나머지 기준정보·월마감 기록은 참고 이력으로 보존합니다.
- 화면을 보는 동안 1분마다, 창으로 돌아올 때, 확인 완료 직후 알림을 갱신합니다. 연결 실패나 범위 초과는 0건으로 표시하지 않고 **? / 확인 필요**로 표시합니다.
- 한 번에 현재 페이지의 최대 30건을 확인합니다. 다른 ADMIN이 먼저 확인했으면 최초 확인자와 시각을 유지합니다. 확인 기록 수정·삭제나 확인 취소 기능은 제공하지 않습니다.
- 원본 이력 전체의 fingerprint에 확인을 연결합니다. 앱에서 처리한 새 변경은 별도 원본·인덱스로 남아 기존 확인에 묻히지 않습니다. 상세 조회와 확인 시 원본 전체를 다시 검증합니다. 다른 ADMIN의 확인으로 목록이 바뀌면 처음부터 다시 조회합니다.
- 확인 표시는 감사 기록이며 거래 승인·재고 조정이 아닙니다. 거래·재고·원본 이력·월마감 잠금·장부 revision은 변경하지 않고, 마감된 기간의 이력도 확인할 수 있습니다.
- 확인 저장 후 목록 갱신에 실패하면 저장 완료 안내를 유지합니다. **변경 내역 조회**로 목록만 다시 불러옵니다.

### 서버와 접근 경계

`manageErpControl`의 `reviewConfirm`, `reviewAlerts`는 현재 회사의 실제 `ADMIN` 역할을 트랜잭션 안에서 재검증합니다. SUB_ADMIN + MANAGER의 기존 업무 권한은 유지하지만 ADMIN 확인은 대신할 수 없습니다. 회사별 `erpReviewConfirmations`에 변경 ID·원본 fingerprint·최초 확인자·시각을 생성하고 `erpAudit`에 `CHANGE_REVIEW_CONFIRMED`를 남깁니다. 해당 컬렉션의 브라우저 직접 읽기·쓰기는 기존 규칙으로 차단됩니다. 누적 점검함은 `erpReviewInbox`와 `erpReviewState`를 사용하며 두 컬렉션도 브라우저 직접 접근을 차단합니다. 새 패키지나 외부 메시지 발송은 없습니다.

## 반품 후 조회 장애 복구

반품이 확정되었지만 목록 조회에 실패하면 **처리는 완료되었습니다** 안내와 **반영 결과 다시 조회** 버튼을 표시합니다. 버튼은 이미 확정된 결과만 다시 조회하며 반품을 재등록하지 않습니다. 조회 성공 시 미수금·반환 예정액을 확인하고 거래명세표 정정 화면으로 이어집니다. 원본 문서는 보관하고 취소·정정 초안을 거쳐 새 PDF를 발행합니다.

- ERP 서버 회귀 182건과 직접 접근·회사 분리 규칙 1,361건. 실제 ADMIN 검증, 권한 회수, 동시 확인, 최초 확인자 보존, 원본 변경 감지, 누락 이력 거부, 한국시간 월 경계를 포함합니다.

- 이 기능의 배포 범위는 Cloudflare 운영 웹과 Firebase `manageErpControl` 함수입니다. 규칙·인덱스 변경은 필요하지 않습니다.

## 누적 점검함·장기 미확인 구현

- 한국시간 처리일과 오늘의 날짜 차이로 7일 이상을 장기 미확인, 30일 이상을 우선 점검으로 표시합니다. 30일 집계는 7일 집계에 포함됩니다. 지급기일·외상매출 연체와 별개입니다.
- 누적·이전 달까지·7일·30일 건수와 가장 오래된 경과일을 표시합니다. 확인 완료는 실제 ADMIN만 가능하며 ERP관리자는 조회합니다. 기간별 화면의 기존 확인 동작도 같은 목록에 반영됩니다.
- 원본 기록 생성과 작은 요약 인덱스 생성을 동일한 governed transaction에서 처리합니다. 확인 receipt, 감사 기록, 인덱스 상태도 원자적으로 저장합니다. 원본 거래·재고·장부 revision·마감 잠금을 바꾸지 않습니다.
- 기존 자료는 문서 ID 순서로 25개씩 재개 가능한 백필을 수행합니다. 분할 operation 전체를 재검증하고 기존 fingerprint 기반 receipt를 재사용합니다. 완료 전 전체 건수는 null/준비 중이며 부분 값을 정확 합계처럼 표시하지 않습니다. 점검함이 열려 있으면 다음 배치를 이어 요청합니다. 누락·불완전 이력은 실패 처리합니다.
- 완료 후 목록·count 집계는 읽기 전용 트랜잭션으로 조회합니다. cursor는 처리 시각+문서 ID, 회사·필터·한국시간 기준일·원본 장부 및 확인 revision에 묶이며 동시 변경 때 재조회합니다. 인덱스에는 요약만 저장하고 변경 전후는 요청 시 원본을 fingerprint 검증 후 조회합니다.
- 동일 원본은 앱에서 불변입니다. 관리 콘솔 등으로 원본을 직접 수정·삭제하는 운영은 지원하지 않습니다. 원본 무결성 검증 실패 시 확인을 차단하며 임의로 새 fingerprint로 덮어쓰지 않습니다.
- 알림은 화면을 보는 동안 1분마다, 창 복귀, 확인 직후 갱신합니다. 읽기 오류는 ?/확인 필요이며 0건이 아닙니다. 저장 후 읽기 실패는 저장 안내를 유지하고 목록만 재시도합니다.

### 배포 순서

1. `erpReviewInbox`의 `reviewStatus ASC, at ASC` 복합 인덱스를 추가하고 READY 상태를 확인합니다. 기존 인덱스·규칙은 보존합니다.
2. 공통 governed writer를 포함하는 ERP 함수 8개(manageErp, manageErpImport, manageErpCorrection, manageErpFinance, manageErpCustody, manageErpDocuments, manageErpReport, manageErpControl)를 배포합니다.
3. 모든 함수 ACTIVE·소스 일치를 확인하고 이전 함수 호출의 최대 실행 시간 경과 후 웹을 배포합니다. 기존 열린 웹의 월간 reviewAlerts/includeReviews 계약은 유지하므로 이전 writer가 남은 동안 누적 초기화를 시작하지 않습니다.
4. 신규 웹에서 `reviewAlerts scope=ALL`, `workQueue reviewScope=ALL`로 opt-in합니다. 검증 전용 회사에서 과거 자료 준비, 장기 필터, 확인·재조회·알림 감소와 회사 격리를 확인한 후 검증 자료를 제거합니다.

공식 근거: [Firestore 커서](https://firebase.google.com/docs/firestore/query-data/query-cursors), [집계](https://firebase.google.com/docs/firestore/query-data/aggregation-queries), [읽기 전용 트랜잭션과 집계 API](https://docs.cloud.google.com/nodejs/docs/reference/firestore/latest/firestore/transaction).
