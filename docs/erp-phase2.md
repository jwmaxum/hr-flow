# ERP 2단계 Excel 검증·미리보기·DB 확정

2026-11-11. 이번 구현 범위는 제공한 기초재고·거래별 입출고 `.xlsx` 양식을 이용한 회사별 업로드다. 참고 Mockup은 초기 데이터로 등록하지 않는다. 운영 배포는 별도다.

## 사용자 흐름

1. 회사 관리자가 **ERP → Excel 업로드**에서 기초재고 또는 거래별 입출고를 선택하고 양식을 내려받는다.
2. `작성안내!B5`에 확인용 회사명, `B6`에 기초재고 기준일을 입력한다. 파일의 회사명으로 저장 회사나 접근 권한을 바꿀 수 없다.
3. 입력 시트의 10~209행에 실제 데이터를 작성한다. 기초재고는 `이관입력!A:P`, 거래별 입출고는 `거래입력!A:AA`만 사용한다.
4. 회사 창고를 미리 등록한다. 창고가 공란인 행은 기본 창고를 선택하거나 미리보기의 행별 매핑으로 지정한다. 신규 품목·거래처의 등록 여부를 명시적으로 확인한다.
5. **검증 및 미리보기**를 누르면 원본행별 오류와 수량·거래단가·공급가액·세액·출고원가·재고수량/금액의 전후 변화를 표시한다. 이때 품목·거래처·원장·현재고는 변경하지 않는다.
6. 오류를 수정한 파일 또는 매핑 설정을 다시 검증한다. 오류가 하나라도 있으면 파일 전체를 확정할 수 없다. 자동 제외·자동 0 변환·부분 확정은 하지 않는다.
7. 로그인 회사와 미리보기 내용을 확인한 뒤 **DB 반영 확정**을 누른다. 서버가 권한과 최신 재고를 다시 검사하고 회사 DB에 기준정보·원장·현재고·확정 기록을 한 트랜잭션으로 저장한다.
8. **반영된 재고 확인**에서 1단계 품목 검색과 창고별 재고를 확인한다. 최근 50개 업로드 이력을 다시 열거나 원본을 내려받을 수 있다. 검토 취소는 미확정 업로드에만 적용한다.

## 입력과 계산 규칙

- 파일당 최대 3MiB, 입력 200행, 압축 해제 12MiB, ZIP 항목 256개다. 제공한 작성안내·입력·참고/예시 시트만 허용한다.
- `참고데이터`, `작성예시`, 참고 계산 열의 수식 결과는 DB 입력에 사용하지 않는다. 표준 드롭다운은 유지할 수 있다. 입력 셀·머리글·기준일의 수식, 입력 영역을 침범하는 배열 수식, 외부 연결·매크로·삽입 개체·숨김 시트·변조된 XML/셀 위치는 거절한다.
- 품목·창고·거래처 코드는 Excel에서 **텍스트**로 입력하여 선행 0을 보존한다. 수량·단가는 소수점 4자리, 환율·세율은 6자리까지 처리한다. 세율 10%는 숫자 0.1이다. 공란과 0은 다르게 취급한다.
- 기초재고는 기준일 마감 재고이고 KRW 장부금액을 저장한다. 단가 방식은 수량×단가를 원 단위 반올림한다. 금액 방식은 입력 장부금액을 그대로 보존한다. 수량 0·금액 0은 허용한다. 양수 수량·금액 0은 비고에 무상 근거가 필요하다.
- 회사의 기초 기준일은 최초 확정으로 설정한다. 같은 기준일의 다른 품목·창고 기초재고는 추가할 수 있으나, 입출고를 시작한 뒤에는 기초재고를 추가하지 않는다. 이미 기초재고가 있는 품목·창고는 중복 확정하지 않는다.
- 거래일은 기준일 다음 날부터다. 파일을 날짜→처리순서→문서 행번호 순으로 계산한다. 같은 문서의 날짜·순서·입출고구분·거래처·통화·환율은 일치해야 한다. 서로 다른 문서는 같은 날 다른 처리순서를 사용한다. 한 문서의 모든 행을 한 파일로 확정한다.
- 이미 확정한 회사의 마지막 날짜·처리순서보다 뒤의 거래만 확정한다. 과거 거래 추가로 이후 재고원가가 조용히 달라지는 것을 막는다.
- 거래통화는 KRW·USD·EUR·JPY·CNY다. KRW·JPY는 0자리, 나머지는 2자리로 공급가액·세액을 반올림한다. KRW 환율은 1이며 원화 공급가액을 재고 입고금액으로 사용한다. VAT와 판매금액은 재고원가와 구분한다.
- 수량과 금액은 정수 스케일 및 `BigInt`로 계산한다. 출고원가는 품목·창고별 직전 재고금액×출고수량÷직전 수량의 이동평균 원가다. 전량 출고는 잔여 장부금액 전부를 차감한다. 음수 재고를 만들거나 금액이 정확히 저장되는 한도를 넘는 거래는 차단한다.

## 회사별 기준정보

- 기존 품목은 회사 내 코드로 찾는다. 단위가 다르면 차단한다. 이름·규격 차이는 사용자가 기존 품목 사용을 확인해야 하며 원본 설명은 원장에 보존한다.
- 확인한 신규 품목만 생성한다. 기본 매입·판매 단가는 0으로 생성하며 화면에서 별도로 설정한다. 업로드한 실제 거래 단가는 원장에 보존한다. 기존 기본단가와 과거 거래가격은 덮어쓰지 않는다.
- 창고는 기존의 활성 회사 창고만 사용할 수 있다. 다른 회사 ID를 전달해도 다른 회사의 창고를 읽거나 사용할 수 없다.
- 거래처는 코드 또는 국가+등록번호로 찾는다. 등록번호가 없거나 동명 후보가 있으면 기존 거래처 선택 또는 신규 등록 확인이 필요하다. 코드가 없는 신규 거래처에는 회사 내 재사용 가능한 코드를 생성한다. 기존 거래처의 연락처·주소는 자동 덮어쓰지 않는다.

## 원자성·중복·권한

회사 `ADMIN`만 업로드·검토·확정·원본 다운로드가 가능하다. `MEMBER`, `SUB_ADMIN`, 플랫폼 `SUPER_ADMIN`, 정지·탈퇴·만료·비밀번호 변경 대기·취소된 세션은 서버에서 거절한다. 기존 `manageErp`의 일반 회사 사용자 수량 조회 권한은 유지한다.

미리보기에는 당시 기준정보·현재고·회사 원장 상태의 지문을 저장한다. 확정 트랜잭션은 모든 읽기를 마친 뒤 쓰기를 수행한다. 중간에 재고·기준정보·회사 권한이 바뀌면 재검증을 요구한다. 같은 확정 요청을 재시도하면 기존 확정 결과를 반환한다. 파일 SHA-256과 회사 내 거래번호·문서 행번호, 기초재고 품목·창고 중복을 함께 확인하므로 파일명을 바꾸거나 다시 저장해도 같은 거래를 다시 반영할 수 없다.

서버 API는 `manageErpImport` callable의 `template`, `preview`, `list`, `get`, `commit`, `cancel`, `downloadSource`다. 클라이언트가 계산한 금액·수량 또는 저장 경로를 확정 요청에 전달할 수 없다. 회사 경로는 로그인 사용자의 현재 서버 프로필로 결정한다.

| 회사 하위 컬렉션 | 용도 |
| --- | --- |
| `erpImports` | 원본 정보·정규화 입력·매핑·오류·미리보기·확정 상태 |
| `erpMovements` | 확정 행별 기초재고·입고·출고 원장 및 원가·잔량·잔액 |
| `erpDocuments` | 회사 내 거래번호의 유일성·문서 공통 필드 |
| `erpState` | 기초 기준일·회사 원장 버전·마지막 확정 순서 |
| `erpImportReceipts` | 파일 해시별 확정 기록 |
| 기존 `erpItems`, `erpPartners`, `erpKeys`, `erpInventory`, `erpAudit` | 기준정보·고유 키·현재고·감사기록 연계 |

원본은 Storage의 비공개 `companies/{companyId}/erp-sources/{importId}/{sha256}.xlsx`에 저장하며 세대 번호와 해시를 검증한다. 브라우저의 Firestore·Storage 직접 접근은 차단한다. 회사 삭제 시 새 ERP 컬렉션과 원본도 기존 회사 삭제 절차에 포함한다.

## 검증·운영 반영·후속 범위

실제 제공 양식으로 빈 입력, 선행 0, 공란·음수, 금액 방식, 수식 변조, 외부 연결, 압축 크기, 통화·세액·원가 반올림을 검사한다. Firestore Emulator는 미리보기 무반영, 원자적 확정, 동일 파일·재저장 중복, 동시 출고, 최신 권한, 다른 회사 접근, 변경된 미리보기, 거래처 재사용 및 200개 신규 품목 전체 반영을 검사한다. 브라우저에서는 양식 업로드·확인·DB 반영·재고 조회·원본 내려받기를 데스크톱과 모바일에서 검증한다. 합성 데이터와 로컬 에뮬레이터만 사용한다.

새 모듈의 줄 커버리지는 파일 파서 100%, 입력/금액 스키마 100%, 업로드 서비스 97.70%다. 분기 커버리지는 각각 76.64%, 86.89%, 86.43%다. 파일 파서의 분기 커버리지는 80% 목표에 미달하며, 모든 손상된 ZIP/XML의 조합을 다 검사한 것으로 해석하지 않는다. 빌드는 기존 번들 크기 안내를 출력하지만 오류 없이 완료됐다.

전체 브라우저 20개 검사를 먼저 실행한 뒤 실패한 항목을 포함한 관련 6개를 재검증했다. 첫 실행 중 함수 재시작/응답 대기와 업로드 선택자 문제가 있었고, 선택 상자는 접근 가능한 역할로 찾도록 수정했다. 기존 ERP 등록 테스트는 초기 목록 로딩이 끝난 뒤 등록하도록 보완했으며, 새 업로드 테스트는 같은 실행의 기존 품목 테스트 자료와 섞이지 않도록 해당 합성 회사의 ERP 자료를 격리한다. 최종 관련 6개는 모두 통과했고, 앞서 통과한 나머지 14개와 합쳐 20개 시나리오의 최종 상태가 PASS다. 이는 단일 실행 20/20 결과와 구분한다. 운영 계정이나 운영 재고로 시험하지 않았다.

설치된 `read-excel-file`, `yauzl`과 기존 급여 파서의 제한된 스트림 검사 방식을 사용했다. 이미 설치된 XML 파서 `saxen` 11.2.0을 직접 의존성으로 명시하여 네임스페이스·시트 관계·셀 수식을 구조적으로 검사한다. 숫자 계산 라이브러리는 추가하지 않았다. [saxen 공식 API](https://github.com/nikku/saxen), [Firestore 트랜잭션](https://firebase.google.com/docs/firestore/manage-data/transactions), [Firestore 한도](https://firebase.google.com/docs/firestore/quotas).

운영 적용에는 `manageErpImport` 신규 함수, 회사 삭제를 담당하는 `adminDeleteCompanyData`, 1단계 `manageErp`와 클라이언트가 필요하다. Storage·Firestore의 직접 접근 차단을 유지한다. 웹은 Cloudflare Pages 배포 절차를 사용한다. 본 작업에서는 운영 DB에 재고를 넣거나 운영 배포하지 않는다.

이 문서는 2026-11-11 Excel 업로드 구현과 당시 검증 결과를 기록한다. 2026-11-12 후속 작업에서 확정 원장의 취소·반품·조정과 3단계 기간별 총괄·상세 원장·Excel 내려받기를 연결했다. [후속 구현 명세](erp-phase3.md)를 참고한다. 소급 재평가·창고 이동·일반 입출고 수동 입력은 남은 범위이며, 음수 업로드나 확정 자료 삭제로 대체하지 않는다.
