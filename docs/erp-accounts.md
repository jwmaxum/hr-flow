# 거래처 수금·보관품 차용·조합상품 운영

회사 관리자는 ERP의 **미수금·수금**, **보관·차용**, **품목·재고현황**, **출고등록**에서 처리한다. 회사별 자료는 독립적이며 일반 사용자는 수금·소유 거래처·금액 원장에 접근할 수 없다.

## 미수금과 수금

- 확정 출고 공급가액과 부가세를 고객의 청구금액으로 집계한다. 판매 반품과 거래 취소는 차감하고, PDF 발행은 청구금액을 추가하지 않는다.
- 기간별 이월잔액, 순매출액, 부가세, 청구합계, 순수금액, 미수잔액을 거래처·통화별로 조회한다. KRW·JPY는 정수, USD·EUR·CNY는 소수점 두 자리로 저장하며 다른 통화를 합산하지 않는다.
- 거래처·통화·수금일·금액·방법·참조번호·사유를 입력한 뒤 미리보기와 잔액을 확인하고 확정한다. 부분 수금을 지원하며 해당 일자의 미수금보다 많이 받을 수 없다. 매출 없는 선입금은 이번 기능의 범위에 포함하지 않는다.
- 판매 반품으로 잔액이 음수가 되면 환불할 금액이다. 환불을 등록하거나 잘못된 수금·환불을 취소할 수 있다. 기존 기록은 삭제하지 않고 반대 기록과 담당자 이력을 남긴다.
- 기존 출고 매출은 자동 집계한다. 과거 수금은 근거 자료를 확인해 등록해야 하며, 과거 입금액을 추정하여 생성하지 않는다. 수금 처리일은 마지막 수금 처리일 이후여야 한다.
- 수금은 거래처별로 등록하고 출고 문서에 배분한다. 문서별 지급기일과 연체일수·연체금액을 조회할 수 있다. 선입금·상계 및 은행 내역 대사는 후속 범위다.

## 판매 후 보관과 차용 판매

회사 소유 재고와 고객 소유 보관품을 구분한다. 회사 소유 재고는 음수로 허용하지 않는다. **차용 미반환수량**의 음수는 원소유 고객에게 돌려줘야 할 상품 수량이며, 회사 재고자산의 음수 금액을 뜻하지 않는다.

1. 회사 재고를 판매했지만 고객이 가져가지 않으면 출고 방식 **판매 후 보관**을 선택한다. 매출·원가와 회사 재고 차감을 반영하고 구매자를 소유자로 하는 보관 원장을 함께 생성한다.
2. 이미 과거에 판매한 상품이면 **보관·차용 → 기존 판매분 보관 등록**에서 소유 거래처·품목·창고·수량·원판매 증빙을 입력한다. 이 등록은 매출·회사 재고자산을 다시 만들지 않는다.
3. 다른 업체에 먼저 판매할 때 출고 방식 **보관품 차용 판매**를 선택한다. 같은 품목·창고의 다른 고객 소유 보관품과 이번 차용 전체 평가금액(원)을 입력한다. 실제 보관수량을 줄이고 원소유자별 미반환 의무를 생성한다. 새로운 판매처의 매출·미수금은 정상적으로 반영한다.
4. 차용 평가금액을 해당 판매의 원가로 기록한다. **현물 반환** 시 같은 품목·창고의 회사 소유 재고를 이동평균원가로 차감해 원소유자의 보관수량을 복원하고, 실제 반환원가와 배분한 평가금액의 차이를 매출원가에 반영한다. 부분 반환과 원 단위 반올림을 지원한다.
5. 소유 고객이 가져가면 **인도 등록**을 사용한다. 보관수량만 줄어들며 매출·회사 소유 재고를 다시 차감하지 않는다.

판매 반품·취소는 출고 원장에서 처리한다. 보관 후 판매 반품은 실제 보관 중인 수량 범위에서 회사 재고로 복원한다. 차용 판매 반품은 미반환 차용 수량 범위에서 원소유자의 보관품으로 복원하며 회사 재고로 입고하지 않는다. 이미 현물 반환한 수량의 판매 반품은 자동으로 처리하지 않으며 원거래 관계 확인이 필요하다.

보관 등록·인도·현물 반환은 미리보기 후 확정하고 별도 취소 이력을 남긴다. 후속 보관 내용이 변경된 경우 취소를 막으며, 현물 반환 취소는 후속 재고 거래가 없는 경우에만 가능하다. 원장 거래일은 마지막 재고·보관 처리일과 순서가 맞아야 한다.

기존 참고 Excel의 음수 수량을 임의로 보관·차용 원장에 이관하지 않는다. 원소유 거래처, 차용 판매처, 품목·창고·수량, 원판매 증빙, 평가금액을 대사한 후 등록한다. 현재 Excel 입출고 양식은 일반 출고와 조합상품 출고를 지원하고, 보관·차용 방식은 직접 출고등록 화면에서 지정한다.

## 조합상품

- **품목 정보만 등록 → 상품 유형: 조합상품**에서 조합 1개당 구성품과 수량을 입력한다. 구성품은 같은 회사의 활성 일반 품목 1~20개이며 중복·중첩·자기 자신 포함은 금지한다.
- 조합상품은 별도 재고자산을 갖지 않는다. 창고별 출고 가능 수량은 구성품으로 만들 수 있는 완전한 조합 개수다. 실제 출고는 입력한 수량에 비례하며 구성품 수량을 소수점 네 자리까지 정확하게 표현할 수 있어야 한다.
- 출고 시 조합상품의 매출·미수금을 한 번만 기록하고 구성품 재고·원가를 같은 트랜잭션에서 차감한다. 명세표·Invoice에는 판매한 조합상품만 표시한다. 품목별 상세 원장에는 구성품의 재고 차감도 남긴다.
- 판매 당시 구성품·수량·원가를 보존한다. 이후 구성을 바꿔도 과거 판매의 반품은 당시 구성으로 복원한다. 부분 반품의 원가는 실제 복원되는 구성품 원가 합계와 일치한다.
- 조합상품 자체의 입고·실사·금액조정·창고이동은 허용하지 않고 구성품을 처리한다. 이번 단계의 조합 출고는 회사 소유 재고 직접 출고에 적용한다. 보관·차용 거래는 개별 품목으로 입력한다.

## 무결성과 배포

모든 확정은 서버에서 관리자 권한·소속 회사·세션·현재 원장·미리보기 지문을 다시 검사한다. 동일 처리 ID를 재전송해도 한 번만 반영한다. 다른 사용자의 변경이 있으면 새 미리보기를 요구한다. 소유 재고·구성품·보관품·차용 의무와 원장이 부분 반영되지 않도록 Firestore 트랜잭션으로 기록한다.

신규 서버 전용 컬렉션은 `erpReceipts`, `erpReceiptJobs`, `erpCustodyLots`, `erpBorrowings`, `erpCustodyJobs`이며 클라이언트 직접 읽기·쓰기는 차단한다. 회사 삭제 절차와 격리 테스트 정리에도 포함한다.

웹은 `jwmaxum/hr-flow`의 main과 연결된 Cloudflare Pages `hr-flow`에, 백엔드는 Firebase 프로젝트 `weberp-8f25f`의 `manageErpFinance`, `manageErpCustody` 및 변경된 기존 ERP 함수·회사 삭제 함수에 배포한다. 고객 운영 재고나 수금 기록을 배포 검증용으로 생성하지 않는다.


## 출고 문서별 수금 배분·연체

ERP → 미수금·수금 → 출고 문서별 수금 배분·연체에서 처리한다.

- 먼저 수금을 등록하고, 수금별 현황의 **문서에 배분**을 누른다. 같은 거래처·통화의 출고 문서에 금액을 입력해 검증·미리보기 후 확정한다. 한 수금을 최대 50개 문서에 나눌 수 있다.
- 거래번호를 서버에서 정규화한 원출고 ID로 묶는다. 조합상품 구성품과 PDF 재발행은 매출을 중복 생성하지 않는다. 은행 참조번호는 문서 ID로 쓰지 않는다.
- 수금의 미배분액, 환불 후 남은 거래처의 미배분 순수금, 문서 미수잔액을 모두 한도로 검증한다. 과거 수금은 임의로 선입선출 배분하지 않는다.
- 배분 이력에서 **배분 해제** 후 다른 문서에 재배분할 수 있다. 한 배분 건 전체를 역처리하며 삭제하지 않는다. 원수금 취소는 해당 적용일부터 그 수금의 배분을 모두 무효화한다.
- 판매 반품으로 문서 잔액이 음수가 되면 초과 수금으로 표시한다. 기존 배분을 해제한 뒤 남은 청구액만 다시 배분한다. 환불은 순수금에서 차감한다. 문서 잔액 합계 − 미배분 순수금 = 거래처 미수잔액이다.
- 문서별 **지급기일 설정**에서 기일과 적용일을 지정한다. 공란은 미설정이며 임의 기일을 생성하지 않는다. 변경 사유와 적용일을 보존하고 과거 조회에서는 당시 적용된 기일을 사용한다.
- 연체일수는 조회 기준일과 지급기일의 달력 날짜 차이다. 기일 당일은 0일, 다음 날부터 1일이다. 연체금액은 해당 문서의 양수 잔액만 사용한다. 미배분 수금이나 다른 문서의 초과수금은 자동 상계하지 않으므로 문서 연체 합계와 거래처 순미수금은 다를 수 있다.
- 배분·기일은 마지막 매출·수금·배분 처리일 이후, 수금은 마지막 배분·기일 처리일 이후로 등록한다. 원장 20,000행 제한과 응답 크기 제한을 적용한다.

서버 전용 erpSettlements, erpSettlementJobs에 변경 이력을 저장한다. 클라이언트 직접 접근을 차단하고 회사 삭제·격리 테스트 정리 대상에 포함한다. manageErpFinance의 관리자·회사·미리보기 지문·중복 확정 방지 검증을 동일하게 적용한다.

## 원가 미확정 기초재고 표시

원본에 수량은 있으나 원가가 없어 확정하지 못한 품목은 서버 관리 pendingOpening 메타데이터로 원본 위치·기준일·수량·단위를 보존한다. 이관 대기 수량을 보여주되 확정 재고, 출고 가능 수량, 재고자산에 더하지 않는다. 원본 수량 공란은 0으로 바꾸지 않는다. 기본 매입단가 변경만으로 재고를 확정하지 않으며 일반 품목 편집 시 이관 메타데이터를 보존한다.

실제 원가 확인 후 기초재고 Excel로 확정할 때 원본 기준일·수량과 대조하고 이관 대기 기록을 해소해야 한다. 다음 개발 단계는 원가 미확정 품목의 원가 입력·기초재고 확정 처리와 연체 회수 예정일·담당자 관리다.
