# ERP 4단계: Invoice·거래명세표와 회사 인감 PDF

2026-11-12. 기존 ERP 기준정보·확정 출고와 회사 서류 템플릿을 연결한다. 참고 자료의 품목·가격·인감을 운영 회사에 복사하지 않으며 각 회사가 등록한 정보를 사용한다. 이번 작업은 구현과 로컬 검증이며 운영 배포는 별도다.

## 사용 순서

1. 회사 관리자가 **ERP → 거래서류 발행**으로 이동한다.
2. **서류 발급 → 회사 서류 템플릿**에 회사명·주소·대표자·법인 인감을 등록한다. 기존에 등록한 회사는 동일한 이미지와 가로·세로 mm 설정을 그대로 사용한다.
3. **공급자 출력 설정**에 사업자등록번호·업태·종목·은행 정보를 저장한다. Proforma에 필요한 영문 회사명·주소·대표자를 함께 입력한다. 한글 회사명·주소·대표자는 기존 회사 서류 템플릿이 기준이다.
4. 아래 문서 유형을 선택하여 초안을 작성하고 **초안 저장·금액 확인**을 누른다. 금액·거래처·인감 크기를 검토하며 **초안 PDF 미리보기**로 미발행 표시와 인감 없는 시안을 내려받을 수 있다.
5. 확인란을 체크하고 **발행 확정**을 누른다. 문서번호를 서버에서 부여하고 등록 인감이 포함된 PDF를 비공개 보관한다.
6. **발행 PDF 내려받기**는 발행 당시 원본을 반환한다. 목록에서 과거 문서를 다시 열 수 있으며 20건씩 이어서 조회한다.

| 문서 | 입력과 연결 | 출력 |
| --- | --- | --- |
| 영문 Proforma Invoice | 회사 품목·매출 거래처 선택, 영문 품목명·Buyer 이름/주소, 수량·견적 단가·세율·통화·유효기간·결제·배송·무역 조건 | 영문 제목과 필드명, Seller/Buyer, 품목·공급가액·세액·총액, 조건과 인감. 출고 전 견적이므로 재고 원장 연결 없이 작성 |
| 한글 Invoice | 입출고 원장의 확정 출고 문서번호를 불러오고 일부 또는 전체 수량 선택 | 한글 공급자/공급받는자, 품목·단가·공급가액·세액·합계, 원출고 번호·조건·인감 |
| 거래명세표 | 한글 Invoice와 같은 확정 출고 연결 방식 | 제공 참고 양식의 날짜·거래처·사업자번호·품목·수량·단가·공급가액·세액·비고·한글 합계금액·작성/검토/승인/인수란. **공급자 보관용과 공급받는자 보관용**을 한 PDF에 수록 |

Proforma·Invoice는 A4 세로, 거래명세표는 참고 이미지에 맞춘 A4 가로다. 긴 품목은 실제 글자 높이를 측정해 행 전체를 다음 페이지로 옮기고 열 제목을 반복한다. 원화 합계는 거래명세표에서 한글 금액도 표시한다. 다른 통화는 해당 통화의 숫자 금액으로 표시한다. 인감 인쇄는 PDF의 원본 크기/100% 설정을 사용한다.

영문 내용은 담당자가 입력한다. 회사·거래처의 고유 이름, 연락처, 단위와 자유 입력 조건을 자동 번역하지 않는다. Invoice는 거래 청구 문서이며 실제 결제나 전자세금계산서를 발행하지 않는다. 작성/검토/승인/인수란은 출력물 기재란이며 기존 HR 결재 절차를 자동 수행했다는 뜻이 아니다.

## 금액과 중복 발행

- Proforma는 기존 Excel 거래와 동일한 고정 소수점 계산을 사용한다. 수량·단가는 소수 4자리, 세율은 소수 6자리이며 세율 10%는 `0.1`이다. 과세·영세·면세와 세금 포함/별도 단가를 지원한다.
- KRW·JPY는 정수 금액, USD·EUR·CNY는 소수 2자리로 공급가액·세액을 반올림한다. 합계는 반올림된 공급가액과 세액의 합이다. 문서 내 통화는 하나다.
- 한글 Invoice·거래명세표는 확정 출고의 단가·세율·통화·금액을 사용하며 화면에서 임의로 다시 가격을 입력하지 않는다. 부분 발행은 원거래 금액을 선택 수량에 배분한다. 마지막 잔여 수량은 남은 미발행 금액 전체를 사용하여 반올림 잔여를 해소한다.
- 발행 가능 수량은 **원출고 − 누적 반품 − 같은 종류의 유효 발행 수량**이다. 문서 취소 시 해당 발행 수량과 금액만 복원한다. 여러 부분 발행 중 하나를 취소해도 다른 발행본 금액을 바꾸지 않는다.
- Invoice와 거래명세표의 발행 수량은 각각 관리한다. 같은 출고에 Invoice와 거래명세표를 한 번씩 발행할 수 있지만 같은 종류로 수량을 초과해서 발행할 수 없다.
- 초안을 저장할 때와 발행 확정 때 원출고·반품·취소·발행 이력·거래처·공급자 설정을 확인한다. 저장 이후 자료가 바뀌면 초안 재저장을 요구한다.
- 발행 후 출고 취소나 반품이 발생해도 발행 PDF를 자동으로 바꾸지 않는다. 담당자가 문서를 취소·정정한다. 이후 발행 시에는 최신 반품 수량과 미발행 금액을 다시 검사한다.

## 번호·원본 보관·정정

발행번호는 회사·종류·발행 연도별 순번으로 관리한다. 예: `PI-2026-000001`, `INV-2026-000001`, `TS-2026-000001`. 번호는 취소해도 재사용하지 않는다.

발행 트랜잭션은 번호, 발행 당시 공급자·거래처·품목·금액·조건, 인감 설정 버전·치수, 출고별 발행 수량과 감사 이력을 함께 저장한다. 같은 초안 버전의 재시도는 같은 번호를 반환한다. PDF 생성은 트랜잭션 밖에서 진행하며 실패해도 번호와 스냅샷을 보존한다. **PDF 생성·내려받기**로 같은 발행본 생성을 다시 시도한다.

원본 인감/로고는 현재 회사의 `official-assets/{sha256}.png|jpg`인지 서버가 검사한다. 실제 바이트 해시·형식·크기와 이미지 해상도를 검증한 뒤 그대로 별도 보관한다. 인감의 배경 제거·재작성·이미지 변환은 수행하지 않는다. PDF에는 회사에 등록된 가로·세로 mm를 적용한다.

이미 보관한 동일 이미지는 무결성을 검사한 뒤 재사용한다. 로고와 인감이 같은 파일이어도 보관 버전을 다시 쓰지 않는다. 발행 스냅샷의 해시는 중첩 필드명을 정렬하여 계산하므로 DB가 맵 필드 순서를 바꾸어도 동일하고, 품목 행 순서나 금액·내용의 변경은 감지한다.

처음 성공한 PDF 파일은 Storage 세대 조건 `ifGenerationMatch: 0`으로 보존한다. 다운로드 시 회사·문서·스냅샷 연결과 파일의 세대·크기·해시를 검사한다. 회사명·거래처·품목·인감이 바뀌어도 기존 PDF는 그대로다. 이미 생성 완료한 파일이 누락되거나 변조되면 현재 정보로 다시 만들지 않고 오류를 반환하므로 보관본 복구가 필요하다.

**문서 취소**는 3~500자의 사유와 확인이 필요하다. 기존 PDF를 삭제하지 않고 취소 이력을 남기며 화면과 다운로드 파일명에 취소된 원본임을 표시한다. PDF 내용 자체는 취소 전 원본 그대로이므로 유효 문서로 재사용하지 않는다. 취소한 원본당 **정정 초안**을 하나 만들 수 있고, 수정·저장·발행하면 새 번호를 받는다. 원본·정정본 번호와 차수를 서로 추적할 수 있다.

발행·취소·정정·PDF 다운로드는 `erpInventory`, `erpMovements`, `erpImports`, `erpState`에 쓰지 않는다. 재고 입출고와 문서 발행은 별도 확정이다.

## 권한과 저장 구조

- 활성 회사의 `ADMIN`만 거래서류·금액·인감 포함 PDF에 접근한다. `MEMBER`, `SUB_ADMIN`, 플랫폼 `SUPER_ADMIN`에는 자동 발행/다운로드 권한을 주지 않는다.
- 서버에서 현재 사용자·회사·상태·세션·구독 기간을 확인하고, 트랜잭션과 PDF 반환 직전 다시 확인한다. 클라이언트도 다운로드 전에 로그인 회사와 권한이 유지되는지 검사한다.
- Firestore와 Storage 원본의 브라우저 직접 접근은 기존 규칙으로 차단한다. 공개 URL이나 영구 다운로드 토큰을 생성하지 않는다.
- 새 callable: `manageErpDocuments` (512MiB, 120초, 인스턴스당 동시 실행 1).
- 회사 하위 컬렉션: `erpIssuedDocuments`, `erpIssueCounters`, `erpIssueAllocations`, `erpPrintSettings`. 기존 `erpAudit`에 문서 동작을 기록한다.
- Storage: `companies/{companyId}/erp-issue-assets/`와 `companies/{companyId}/erp-issued-pdfs/`. 회사 삭제 절차에 새 컬렉션을 포함했고 파일은 기존 회사 경로 삭제 절차에 포함된다.
- 발행 문서당 1~100행, 연결 가능한 원출고 문서 최대 200행, PDF 최대 60페이지·5MiB, 원본 인감/로고 각각 3MiB·4096px로 제한한다. 문서가 너무 크면 발행 수량/행을 나누어 작성한다.
- 문서 원본과 번호 카운터가 중요하므로 운영 백업·복구 대상에 새 컬렉션과 비공개 Storage 경로를 포함한다. PDF 생성 전 중단된 발행본은 보존된 스냅샷과 인감으로 재개할 수 있다.

## 검증 결과

로컬 `demo-` 에뮬레이터와 합성 회사·인감으로 검증했으며 운영 데이터는 사용하지 않았다.

| 항목 | 결과 |
| --- | --- |
| 클라이언트 빌드·TypeScript | `npm --prefix client run build` 통과. 기존 공통 번들 약 894kB에 대한 500kB 경고는 남음 |
| 린트·클라이언트 단위 검사 | 린트 통과, 단위 검사 128건 통과 |
| 서버 회귀 | ERP·기존 공문·회사 삭제 133건, 급여 60건 통과. 이후 수정한 발행·PDF 범위 19건을 다시 실행해 모두 통과 |
| 발행 코드 커버리지 | 최종 범위 검사: 행 99.32%, 분기 85.25%, 함수 97.94% |
| 회사 격리·보안 규칙 | Firestore/Storage 규칙 1,179건 통과. 운영/E2E 빌드 경계 65파일 통과 |
| PDF 출력 | 기본·장문 6종 33페이지의 A4 크기·글자 경계·품목 누락·합계 검사 통과. 대표 페이지와 로고 포함 출력 시각 검토, 최종 렌더러 검사 3건 통과 |
| 보안·변경 검토 | 새 코드의 비밀값·임의 코드 실행·공개 파일 URL·디버그 출력 검사 이상 없음. 회사/역할/세션 재검증, 입력 한도, 원본 해시, 취소·발행 트랜잭션 검토 및 `git diff --check` 통과 |

브라우저는 ERP·회사 격리 시나리오를 PC/모바일에서 선택 검증했다. 기존 기준정보·Excel·원장·격리 8건이 통과했으며 새 거래서류 발행 2건도 최종 재실행에서 통과했다(종료 코드 0, 재시도 0). 세 PDF 다운로드, 인감 변경 후 원본 유지, 취소 원본 다운로드, 정정본 새 번호, 재고 불변, 일반 직원 접근 차단을 확인했다. PC·모바일 화면과 실제 다운로드한 세 PDF도 검토했다. 전체 애플리케이션의 모든 E2E를 실행했다는 의미는 아니다.

검증 중 동일한 로고·인감 보관 파일의 재쓰기, DB 맵 필드 순서 변경에 따른 원본 검사 실패를 수정하고 각각 회귀 검사를 추가했다. 실제 운영 Storage의 동시 생성 조건, 회사의 실인감과 실물 인쇄, 운영 배포 후 점검은 5단계에서 수행한다.

## 서비스 반영과 다음 단계

운영 반영 시 기존 3단계 인덱스 준비 상태를 확인하고 Firebase Functions와 Cloudflare Pages 웹을 배포한다. 이번 단계에서 추가 Firestore 복합 인덱스는 필요하지 않다. 회사별 등록 인감과 영문 출력 정보를 확인한 뒤 소량 시범 발행으로 화면·원장·PDF 금액을 대사한다.

다음은 개발계획서 **5단계 시범 운영과 서비스 배포**다. 지정 회사의 실제 입력 양식으로 이관을 모의 실행하고, 부분 반품·문서 정정·재다운로드·A4 실물 인쇄를 담당자와 확인한다. 운영 배포 후 권한별 접근, 원본 보관, 백업 복구까지 확인한 뒤 적용 회사를 확대한다.

## 재사용·조사 근거
