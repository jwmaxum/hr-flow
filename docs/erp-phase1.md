# ERP 1단계 기준정보와 재고 조회

HR Flow 브랜드 오른쪽 ERP 버튼으로 `/erp`에 진입한다. 모바일 상단에도 HR Flow 오른쪽에 ERP 진입 버튼을 제공한다. 회사별 품목, 창고, 거래처를 등록·수정하고 품목명 또는 코드 앞부분으로 재고를 찾는다. 같은 이름의 품목은 코드로 구분한다.

## 권한과 데이터 구분

| 사용자 | 허용 기능 |
| --- | --- |
| 회사 관리자 `ADMIN` | 품목·매입/판매 단가·창고·거래처 등록/수정/사용 중지, 재고수량·금액 조회 |
| 활성 회사 사용자 `SUB_ADMIN`, `MEMBER` | 소속 회사 품목·창고 목록과 재고수량 조회. 단가·재고금액·거래처 상세는 서버 응답에서 제외 |
| 플랫폼 운영자 `SUPER_ADMIN`, 퇴사·정지·구독 만료 사용자 | 회사 ERP 접근 불가 |

회사는 서버의 현재 `UserProfile`과 활성 회사·구독·세션으로 확인한다. 요청의 companyId는 현재 화면이 같은 회사인지 비교하는 값이다. 경로 선택이나 권한 부여에 그대로 사용하지 않는다. 저장 트랜잭션 안에서 권한을 재검사하고 목록 조회 후에도 변경된 권한을 확인한다.

각 회사는 품목코드·이름·단가를 독립적으로 입력한다. 예를 들어 두 회사의 `0001`은 별개 품목이다. 106개 참고 품목이나 Mockup 재고를 자동 등록하지 않는다.

## 기준정보 관리

- 품목은 코드, 품목명, 규격, 단위, 매입단가, 판매단가, 과세구분, 그룹, 비고, 사용 상태를 관리한다. 단가는 KRW이며 0 이상, 소수점 4자리 이하를 허용한다.
- 창고는 코드, 창고명, 주소, 비고, 사용 상태를 관리한다.
- 거래처는 코드, 이름, 매입/매출 유형, 국가코드, 등록번호, 담당자, 이메일, 연락처, 주소를 저장한다. 저장한 거래처는 검색해 다시 수정·사용할 수 있다. 등록번호가 없는 동명 거래처는 자동 병합하지 않는다.
- 코드의 앞뒤 공백, 유니코드 호환 문자와 대소문자를 정규화해 회사·종류별 중복을 차단한다. 거래처는 국가와 등록번호의 중복도 검사한다.
- 코드와 별개인 자료 ID를 유지한다. 변경 시 `expectedRevision`을 대조하여 다른 사용자의 수정을 덮어쓰지 않는다.
- 사용 중지는 자료와 재고를 보존한다. 확정 원장의 삭제 기능은 제공하지 않는다. 기본 단가 변경이 기존 재고금액을 바꾸지 않으며, 재고 기록이 있는 품목의 단위 변경을 차단한다.

## 품목 검색과 현재고

품목명이나 코드의 앞부분을 입력하면 회사 내 목록을 검색하고 첫 결과의 재고를 표시한다. 다른 품목을 선택할 수 있으며 목록은 50개씩 더 불러온다. 검색어 변경·회사 변경·늦은 응답으로 이전 품목이나 다른 회사 자료가 남지 않도록 조회 결과를 구분한다.

재고가 기록된 품목은 창고별 수량과 합계를 표시한다. 관리자는 재고금액도 조회한다. 실제 수량 0은 `0`, 재고 원장이 아직 없는 품목은 `재고 미등록`으로 구분한다. 이 단계에서는 수량을 임의 수정하거나 기본 단가×수량으로 재고금액을 추정하지 않는다.

## 서버와 저장 구조

Firebase callable `manageErp`가 `list`, `save`, `inventory` 요청을 처리한다. 브라우저의 직접 Firestore 접근은 차단하고 서버가 허용 필드만 반환한다. 독립적인 기존 Firebase 인증·회사 권한 검사와 callable 토큰 취소 확인을 재사용했다.

회사 문서 아래 다음 컬렉션을 사용한다.

| 경로 | 내용 |
| --- | --- |
| `companies/{companyId}/erpItems/{id}` | 품목, 기본 단가, 검색 키, revision |
| `companies/{companyId}/erpWarehouses/{id}` | 창고 기준정보 |
| `companies/{companyId}/erpPartners/{id}` | 회사 거래처 |
| `companies/{companyId}/erpKeys/{hash}` | 코드·거래처 등록번호 중복 방지 예약 |
| `companies/{companyId}/erpAudit/{id}` | 변경 사용자·자료 ID·버전·시점 |
| `companies/{companyId}/erpInventory/{id}` | 서버가 확정한 현재고. 1단계에서는 조회만 수행 |

현재고 문서는 `companyId`, `itemId`, `warehouseId`, `quantity`, `value`, `currency: KRW`, `updatedAt`를 사용한다. 수량은 품목의 재고 단위, value는 원 단위 정수 재고금액이다. 품목·창고마다 하나의 현재고 문서를 사용하며 회사·창고 연결이나 중복이 잘못되면 합계를 추정하지 않고 오류로 표시한다. 읽기는 트랜잭션으로 동일 시점의 현재고를 조회한다.

회사의 전체 삭제 절차에 ERP 하위 컬렉션 정리를 포함했다. 다른 회사의 기준정보와 재고는 보존한다.

## 검증과 배포

Firestore Emulator 테스트는 회사별 동일 코드·상이한 가격, 권한 우회, 동시 중복 등록, 코드 변경, 이전 버전 수정, 검색 페이지, 거래처 중복, 재고 없음/0, 창고별 합산, 가격 비공개와 단위 변경 제한을 검증한다. 직접 Firestore 읽기·쓰기는 Security Rules 테스트에서 거절한다.

격리된 브라우저 테스트는 데스크톱·모바일에서 실제 로그인 후 ERP 버튼, 창고·품목·거래처 등록/수정, 검색과 재고수량, 회사 간 분리, 일반 사용자의 조회 권한을 검증한다. 운영 데이터와 연결하지 않는다.

로컬 실행 환경은 기본 샌드박스에서 루프백 연결이 차단되어 허용된 실행 환경으로 전환했다. Playwright 전용 Chromium 설치가 없어 설치된 Chrome을 임시 테스트 프로필로 사용한다. CI는 기존 워크플로의 Chromium 설치 단계를 사용한다.

운영 반영 대상은 `manageErp` 신규 함수, ERP 자료 삭제를 포함한 `adminDeleteCompanyData` 함수, Firestore 규칙과 클라이언트다. 서버·규칙을 적용한 뒤 웹은 기존 Cloudflare Pages 절차로 배포하고 Firebase Hosting은 사용하지 않는다. 별도 복합 인덱스나 Mockup 이관은 필요하지 않다. 본 작업의 요청 범위는 구현이며 운영 배포는 별도로 수행한다.

다음 2단계에서는 작성한 Excel 양식의 파일 검증·미리보기, 거래처 및 품목 매핑, 기초재고·입출고 원장 확정, 동시 출고와 재업로드 중복 방지를 구현한다. ERP 담당자에게 쓰기 권한을 위임하는 세부 권한 관리도 이 단계에서 확장할 수 있다.
