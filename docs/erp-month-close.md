# ERP 월마감·권한·승인 운영

## 사용 위치

ERP → **관리자 관리**에서 월마감·보고서 보관, 담당자 권한, 승인 요청, 수정·삭제 이력을 관리한다. 회사 ADMIN은 전체 권한을 갖는다. 회사 대표 가입자도 DB 역할이 ADMIN이므로 같은 기능을 사용한다. 플랫폼 SYSTEM_ADMIN은 회사 ERP 권한을 자동으로 갖지 않는다.

## 담당자 지정

ADMIN이 같은 회사의 활성 SUB_ADMIN·MEMBER에 접근 없음 / 조회 전용 / 입고 담당 / 출고 담당 / 입출고 전체를 지정한다. HR 역할과 ERP 권한은 별도이며, 지정하지 않은 직원은 ERP 화면과 API에 접근할 수 없다. 권한 변경은 서버 API로만 처리하고 관리자·대상 직원·변경 전후 권한·사유를 기록한다. 직원 프로필의 실시간 갱신으로 메뉴도 변경되며 서버는 모든 요청과 확정 트랜잭션에서 현재 권한을 다시 검사한다.

담당자는 지정 방향의 직접 입출고, 품목·창고·거래처 등록, 재고·원장 조회를 사용한다. 출고 담당자는 외상/입금완료 출고를 체크할 수 있다. 입금완료는 회사가 자체 확인한 내용을 등록하는 것으로 은행 연동은 없다. 입출고 전체 담당자는 창고 이동도 처리한다. Excel 이관·기초재고 원가 확정·미수금·보관차용·거래서류 발행·월마감·권한 부여는 ADMIN이 담당한다.

## Sub_ADMIN의 ERP관리자 옵션

회사 ADMIN이 활성 Sub_ADMIN에게만 **ERP관리자(MANAGER)**를 지정할 수 있다. 조직관리의 직원 ERP 접근 옵션과 ERP 관리자 관리 → 담당자 권한에서 같은 API를 사용한다. MEMBER에게는 이 옵션을 표시하지 않으며 서버도 지정을 거부한다. 사용자 역할을 ADMIN으로 변경하거나 수금·문서 발행·Excel 이관·권한 부여·타인 승인·월마감 권한을 함께 주지 않는다.

ERP관리자는 양방향 직접 입출고·창고 이동을 사용하고, 판매/매입 반품, 원입출고 문서 취소, 실사 수량/장부금액 조정, **품목 매입·판매 단가만 변경하는 수정**을 ADMIN 승인 없이 확정한다. 이름·구성·사용 상태 등 다른 품목 정보와 함께 수정하거나 창고·거래처 기준정보를 변경하면 기존 승인 요청으로 처리한다. 기초재고나 보정 거래 자체의 취소도 기존 승인 절차를 유지한다. 승인 대기 중인 요청을 권한 변경만으로 직접 확정할 수 없으며, ADMIN이 기존 요청을 먼저 처리해야 한다.

직접 처리도 회사별 원장·변경 전후 값·처리자·사유·시간을 같은 트랜잭션에서 보관한다. 이력에는 **ERP관리자 직접 처리**로 표시하며 ADMIN이 승인한 것처럼 기록하지 않는다. 월마감 잠금은 동일하게 적용한다. 서버는 현재 활성 상태·SUB_ADMIN 역할·MANAGER 옵션을 함께 검사하므로 역할 강등, 퇴사 또는 ERP 권한 회수 후에는 직접 처리할 수 없다. ERP 옵션은 HR 역할과 별도로 보관되므로 HR 역할/재직 상태를 바꿀 때 기존 ERP 옵션도 함께 확인한다.

## 수정·삭제 승인

위 ERP관리자 직접 처리 예외 외에는, 기존 기준정보의 단가·내용 수정과 사용 중지, 확정 입출고의 취소·반품·수량/장부금액 조정은 담당자가 검증한 뒤 승인 요청한다. 승인 대기에는 실제 재고가 변하지 않는다. ADMIN은 요청의 전후 값과 사유를 확인하고 승인·반영 또는 반려한다. ADMIN의 직접 수정 저장·조정 확정은 관리자 승인 행위로 기록한다.

승인할 때 원거래·재고·기준정보·요청자 권한·마감 상태를 다시 검증한다. 미리보기 이후 원장이 바뀌면 승인을 거부하며 담당자가 다시 검증해야 한다. 이미 승인된 요청은 재실행하지 않는다. 요청·반려 기록도 남는다. 기존 거래를 실제로 삭제하거나 덮어쓰지 않고 역거래·보정 거래를 추가한다. 기준정보 삭제에 해당하는 사용 중지도 과거 원장을 유지한다.

신규 기능 적용 이후 처리의 변경 전후 자료, 처리자, 요청자, 승인자, 사유, 시간을 `erpChangeHistory`에 추가 전용으로 기록한다. 입출고/재고/단가/취소/문서/수금 변화가 같은 트랜잭션에서 보관된다. 이전 거래는 기존 ERP 원장과 `erpAudit`에서 유지하며 소급해 존재하지 않던 전후 값을 만들어 넣지 않는다.

## 월마감과 재개방

### 승인 대기 알림

회사 ADMIN의 상단 ERP 확인 아이콘에 현재 승인 대기 건수를 표시한다. 로그인·창 복귀 시와 화면을 보고 있는 동안 1분마다 서버에서 다시 조회한다. 100건을 넘으면 `100+`로 표시하며, 연결 실패를 0건으로 표시하지 않는다. 알림을 누르면 ERP 승인 요청 탭으로 이동한다. 대기 건수는 기존 승인 원장에서 직접 조회하므로 이미 대기 중이던 요청도 표시하고, 승인·반려 후 줄어든다. 알림을 열어 보는 것으로 요청이 처리되지는 않는다. 이메일·문자 발송이나 은행 연동은 사용하지 않는다.

### 체크리스트와 증빙

새 월마감에는 다음 5개 항목을 ADMIN이 확인·저장해야 한다: 재고 수량·금액 대사, 매출·매입 및 취소·반품 내역, 외상매출·수금·미수잔액 자체 확인, 승인·가격 조정 검토, 원가 미확정 품목의 자산 제외 확인. 항목별 메모와 확인자·확인 시각을 기록한다. 중간 저장이 가능하며 모든 항목을 확인하기 전에는 마감할 수 없다.

증빙은 PDF·PNG·JPG·GIF·WEBP를 최대 5개, 파일당 5MiB·합계 20MiB까지 첨부한다. 별도 증빙이 없으면 3자 이상의 미첨부 사유를 저장한다. 체크리스트의 미저장 입력이 있으면 마감 확정·증빙 변경을 차단한다. 파일 내용·확장자·형식·크기·회사·월·원본 해시를 서버에서 검증하고, 원본은 비공개 Storage에 생성 전용 조건으로 저장한다. 공개 다운로드 URL이나 브라우저의 직접 Storage 쓰기는 제공하지 않는다.

체크리스트 저장·증빙 첨부·제외는 버전 확인과 감사 이력을 함께 기록한다. 제외 시 사유가 필요하며 이전 마감 보관본의 증빙은 제거하지 않는다. 마감 미리보기 후 체크리스트·증빙이 변경되거나 보고서를 생성하는 동안 변경되면 다시 미리보기해야 한다. 마감된 월의 확인 사항·증빙은 잠기고, 재개방하면 5개 항목을 다시 확인해야 한다. 기존 증빙은 재사용하거나 사유를 남겨 제외할 수 있다.

마감 보고서 Excel·PDF에도 확인 항목과 증빙 목록을 포함한다. 마감 버전마다 체크리스트와 증빙 연결을 복사해 보존하며, 보관함에서 당시 확인 기록과 증빙 원본을 내려받는다. 체크리스트 도입 이전 보고서는 원본을 유지하고 당시 존재하지 않았던 확인 기록을 소급 생성하지 않는다.

월말이 지난 월만 마감할 수 있다. 첫 마감 이후 다음 달 순서대로 진행한다. 미리보기에는 전체 재고자산·순매출·순매입·원가 미확정 품목 수를 표시한다. ADMIN이 제외 품목과 금액을 확인하고 사유를 입력하면 마감한다. 원가 미확정 품목은 당시 보고서에 대기 건수로 명시하고 재고자산에는 포함하지 않는다. 대상 기간의 승인 대기 요청이 있으면 먼저 승인 또는 반려해야 한다.

마감 후 해당 월말까지의 입출고·기초재고·조정·보관/차용·수금·배분·기일 변경·거래서류 변경을 차단한다. 최초 마감은 그 이전 일자도 잠근다. ADMIN도 마감 검사를 우회하지 못한다. 회사별 마감 상태와 원장 변경을 같은 Firestore 트랜잭션에서 읽어 동시 마감과 확정의 경합을 방지한다.

재개방은 가장 최근 마감 월부터 역순으로, 사유를 남겨 처리한다. 다시 마감할 때는 재개방 월부터 순서대로 새 버전을 생성한다. 기존 원장 규칙(마지막 처리일 이후 등록, 후속 거래가 연결된 원거래의 취소 제한)은 재개방해도 유지한다. 후속 기간 거래가 있으면 해당 거래 관계를 먼저 정리하거나 현재 열린 기간에 보정 거래를 등록해야 한다.

## 월마감 일정·담당자·미완료 알림

ERP → **관리자 관리 → 월마감 일정**에서 ADMIN이 대상 월, 마감 예정일, 총괄 담당자와 5개 확인 항목의 담당자를 지정한다. 예정일은 대상 월말 이후 날짜이며, 담당자는 같은 회사의 활성 ERP 접근자만 선택할 수 있다. 저장 시 버전을 확인하고 사유·변경 전후 값을 감사 이력에 기록한다. 기존 회사에 임의의 일정이나 담당자를 자동 생성하지 않는다.

담당자는 본인에게 배정된 항목에 완료 보고 메모를 처음 등록할 수 있다. 완료 보고는 ADMIN의 최종 체크리스트 확인과 별개이며, 보고 내용을 직접 덮어쓰거나 삭제할 수 없다. ADMIN은 사유를 남겨 보고를 초기화하거나 담당자를 변경한다. 담당자가 변경되면 해당 항목의 기존 보고는 현재 일정에서 초기화하고 이전 값은 감사 이력에 보존한다.

상단 달력 아이콘은 ADMIN에게 확인·최종 마감이 남은 일정 수, 담당자에게 본인의 미보고 항목이 남은 일정 수를 표시한다. 기한 경과는 서버의 한국 날짜와 예정일을 비교한다. 클릭하면 담당자 일정 화면으로 이동하며 로그인·창 복귀·앱 내 작업 완료 후와 화면을 보고 있는 동안 1분마다 갱신한다. 이메일·문자 발송이나 별도 Cloud Scheduler는 사용하지 않는다. 조회는 최대 100개 진행 일정이며 초과 여부를 표시한다. 완료 보고 후에도 ADMIN 확인과 실제 마감 전까지 관리자 알림은 유지된다.

마감 확정 시 일정을 CLOSED로 변경하고, 당시 예정일·담당자·완료 보고를 보관본과 Excel/PDF 보고서에 포함한다. 재개방 시 일정은 OPEN이 되고 완료 보고를 다시 받으며 과거 보관본은 유지한다. 보고서 생성 중 일정이 변경되면 마감은 원자적으로 중단한다. 일정 등록이 없던 과거 마감도 기존 방식으로 처리할 수 있다.

**별도 ERP 접근 옵션:** 조직관리 → 직원 정보 수정 또는 인사관리 → 직원 상세 → ERP 접근 권한에서 접근 허용 여부와 조회/입고/출고/입출고 전체 옵션을 저장한다. HR 역할은 변경하지 않는다. 회사 ADMIN은 ERP 접근을 자동으로 가지며 이 옵션으로 회수할 수 없다. 조회 전용 사용자는 재고·기준정보·입출고 원장을 조회할 수 있지만 등록·보정 미리보기·수정/취소 요청·승인을 할 수 없다. 입출고 담당자의 수정/취소 요청은 기존대로 ADMIN 승인 이후에만 반영한다. 권한을 조회 전용이나 접근 없음으로 변경하면 과거 미리보기 확정과 승인 대기 요청 실행도 차단한다.

서버 전용 컬렉션은 erpClosePlans이며 OPEN 상태/월 정렬과 담당자 배열 조회 인덱스를 사용한다. 직원 프로필의 ERP 권한은 기존 감사 포함 grant API로 변경하고 브라우저의 직접 쓰기는 계속 차단한다.

## 보고서 보관

마감 시 전체 자료로 Excel과 PDF를 서버에서 생성하고 비공개 Storage에 파일 자체를 보관한다. 큰 PDF는 800행씩 번호가 붙은 분권으로 나누며 내역을 생략하지 않는다. 현재 원장 조회의 각 20,000행/자료 5MiB 한도와 각 파일 5MiB 한도를 초과하면 마감을 실패 처리한다. 파일 생성·저장·무결성 검증이 끝나고 원장 버전이 동일할 때만 마감과 보관본 메타데이터를 함께 확정한다. 실패하면 부분 마감은 게시하지 않는다.

보관 파일은 회사·마감 버전·내용 해시 경로와 `ifGenerationMatch:0` 조건으로 생성한다. 다운로드 시 회사 권한, 파일 세대, 크기와 SHA-256을 재검증하고 당시 저장한 바이트를 반환한다. 현재 자료로 과거 파일을 재생성하지 않는다. 재개방·재마감은 v2, v3 등 새 버전이며 v1은 그대로 남는다. 일반 ERP 기능에는 보관본·감사 기록 삭제 API가 없다. 별도로 명시 승인받아 수행하는 플랫폼 회사 전체 삭제는 기존 데이터 삭제 정책을 따른다(클라우드 운영자까지 막는 WORM 보존 잠금은 적용하지 않음).

## 검증과 배포

`functions/tests/erp-governance.test.js`에서 권한 분리·승인 대기·승인 중복·기준정보 수정·마감 잠금·보관본 변조·재개방·원장 경합·렌더 실패를 검증한다. 기존 ERP 회귀, 프로필 권한 및 ERP 컬렉션 직접 접근 규칙, 클라이언트 세션 변경 차단, 데스크톱·모바일 관리 화면과 다운로드를 함께 검증한다.

서버는 `manageErpControl`에서 마감·체크리스트·증빙·승인 알림을 처리하고 ERP callable 7개에 공통 승인·감사·마감 검사를 적용한다. `erpApprovals(requestedBy ASC, createdAt DESC)`와 `erpApprovals(status ASC, createdAt ASC)` 인덱스를 사용한다. `erpCloseChecklists`는 회사별 서버 전용 컬렉션이며 기존 Firestore/Storage의 직접 접근 차단을 유지한다. 웹은 `jwmaxum/hr-flow` main → Cloudflare Pages `hr-flow`에서 배포한다. 운영 회사의 거래·권한·월마감을 테스트로 변경하지 않는다.
